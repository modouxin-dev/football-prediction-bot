# ⚽ Football Prediction Bot

Telegram 足球量化预测机器人：泊松模型给出内部基准，赔率可用时以去水市场概率作为展示口径，每天定时推送，并支持按钮查看深度分析 / 历史交锋 / 赔率对比。部署在 Railway 上。

> ⚠️ 模型只基于进球数据估算，**不构成投注建议**。市场赔率通常比简单模型更准，模型与市场差距大时，先怀疑模型。

## 自动化闭环（自动预测 → 结算 → 复盘）

机器人不只是"被问才答"，而是每天自己跑完一圈：

| 环节 | 周期 | 做什么 |
| --- | --- | --- |
| 自动预测 | 每 6 小时（启动 2 分钟后首跑） | 为 `LEAGUE_IDS` **全部启用联赛** + **欧冠**向前 3 天的比赛生成预测并落库；按 fixture id 覆盖写，重复跑只刷新概率，不产生重复记录 |
| 赛果结算 | 每 6 小时（启动 5 分钟后首跑） | 把已完场的真实比分回写，供命中率统计 |
| 每日复盘 | 每日（`REVIEW_TIME`，默认比推送晚 1 小时） | 统计近 7 天命中率、与**朴素基线**对照、按联赛 / 预测方向 / 信心档 / 口径归因，并推送到群 |

**为什么要有朴素基线**：只报"命中 45%"无法判断好坏——永远猜主队也有接近的命中率。复盘同时给出基线命中率与差值，模型是否真有信息量一目了然。

**默认只出结论、不改参数**：样本少时自动调参会把偶然波动当成规律，反而越学越差。样本不足的分组只报数量不报命中率（3 场全中显示 100% 会骗人）。

> **自动预测必须与赛程同步覆盖同一批比赛**。赛程同步遍历 `LEAGUE_IDS` 的全部联赛；自动预测若只跑主联赛，其余联赛在看板上就恒显示「尚未生成预测」——有赛程却没预测。因此这里取 `settings.league_ids`（并补上欧冠），窗口 3 天以覆盖看板「3 天」视图。
>
> **配额按联赛轮转发牌**，不是先到先得。否则 `cap` 打满后直接结束，排在后面的联赛（意甲 / 西甲）一场都轮不到。轮转保证配额不足时每个联赛都分到一些。
>
> **看板侧同样要过滤**：本地库存着历史同步进来的全部比赛，`/fixtures` 若只按日期取，未配置联赛（如历史残留的哥伦比亚）会列进看板，而这些比赛永远不会有预测、恒显示「尚未生成预测」。因此 `/fixtures` 按 `LEAGUE_IDS` 映射出的分区代码过滤；映射不出任何代码时**不过滤**——宁可多显示，也不能因映射表缺项让看板整页空白。

### 多联赛

填 `LEAGUE_IDS=39,140,78` 即可同时跑多个联赛，赛程按开赛时间合并排序。

**隔离保证（已用测试锁死）**：每个联赛用**自己的积分榜**建模、赛果**只更新本联赛**的 Elo 评分、数据按联赛分区存放。不会出现「拿英超积分榜预测西甲比赛」这类串味。

已内置映射：英超 `39` · 西甲 `140` · 德甲 `78` · 意甲 `135` · 法甲 `61` · 欧冠 `2` · 荷甲 `88` · 葡超 `94` · 英冠 `40` · 巴甲 `71` · 世界杯 `1` · 欧洲杯 `4`。

请求量估算：12 联赛 × (同步 1 + 赔率 3) ≈ 48 次/天，Pro 套餐（7500/天）绰绰有余。

> 单联赛失败不会拖垮整体——某个联赛拉取失败时其余联赛照常入库，只有全部失败才记失败。

### 主数据源套餐与配额

| 套餐 | 日请求 | 历史赛季 | 赔率 | 伤停 |
| --- | --- | --- | --- | --- |
| Free | 100 | ❌ 受限（仅「当年−4 ~ 当年−2」） | ✅ | ✅ |
| **Pro** | 7,500 | ✅ 全解锁 | ✅ | ✅ |
| Ultra / Mega | 75,000 / 150,000 | ✅ | ✅ | ✅ |

> 伤停与赔率**免费档就有**，付费档真正买的是**历史赛季深度**
> （免费档按日期范围请求历史赛季会被套餐拒绝，这是主源历史上快速失败的常见原因）。

**`/status` 的「📊 今日请求」**同时显示两路计数：
- `主源 X / 7500` —— 官方端点自报（有延迟，可能缺失）
- `本地实测 主源 N` —— 本项目自己记的**实际发出**请求数

两者不必相等：主源失败并切换备用源时，**一次 `/predict` 实际消耗 2 次**。
备用源（football-data.org）免费层**没有额度查询端点**，所以只显示本地实测值，
不再出现 `? / ?`。


### 主源自诊断（`/diag`）

`/diag` 绕开调度层**直连主源**，输出冷却状态、主源记录、可用赛季、多联赛赛程探测、赔率与伤停端点探测。

**为什么多联赛探测**：主联赛在休赛期或国际比赛日会整体停摆，而欧冠照常开踢——只看主联赛会误判成"主源不可用"。探测池 = 主联赛 + 欧冠 + 其余四大联赛（上限 5 个），任一有比赛即判主源可用；全部为空时如实说明"无法区分"，**不替你下结论**。

**空结果 ≠ 故障**：整季赛程返回空列表时**不会**触发切换备用源。历史行为是一次空结果就把数据源身份永久改成 football-data，而该备用源**不提供赔率与伤停**，直接导致这两项全线消失——这正是"明明订阅了 Pro 却显示数据不足"的根因。

## 架构

命令走 **Command Pattern**：`main.py` 只装配依赖并注册，`commands/` 下每个模块
负责一类指令，`CommandDispatcher` 统一查表 + 权限拦截 + 调用。新增一条指令只需
在对应模块 `register` 一行，**入口文件不会因此变长**。

```
main.py            装配 + 注册 + 启动（760 行，重构前 1242 行）
├── commands/      指令层：basic / matches / admin + dispatcher
├── scheduler.py   定时推送、赛程同步、赛果结算 + NotificationManager
├── support.py     权限、异常翻译、消息渲染（被命令层与调度层共用）
├── service.py     业务逻辑（SSOT）
└── repository.py  SQLite（WAL + 原子事务 + 指数退避）
```

**为什么不引入 apscheduler**：python-telegram-bot 自带 `JobQueue`，已用
`run_daily` / `run_repeating` 实现定时推送。再加一个调度器会形成两个互不知晓的
调度器同时运行，最直接后果是同一场比赛被推送两次。`scheduler.py` 做的是把已有
JobQueue 逻辑抽出来，不是换调度器。

**并发**：`repository.py` 强制 `PRAGMA journal_mode=WAL`，写操作走
`BEGIN IMMEDIATE` 原子事务 + 指数退避重试（20ms→40ms→80ms，带随机抖动防惊群）。
实测 10 线程写 400 场的同时开一个持续读取线程，0 错误。

| 端点 | 用途 |

| `/health` | 健康状态 + 持久化是否生效 |
| `/stats` | 命中率（与 `/stats` 命令同一份数据） |
| `/health/model` | Log Loss 趋势、校准曲线、各信心等级命中率 |
| `/audit` | 预测审计：历史预测 vs 实际赛果 |
| `/strength` | 球队攻防强度榜 |
| `/fixtures` | 赛程 + 队伍近况（近 5 场胜负、实力分、联赛排名、轮次），`?days=1/3/7` 切换天数 |
| `/backtest` | 历史回测结论（时间 / 口径 / 场次 / 命中率 / Log Loss / RPS） |
| `/commands` | 指令清单 |

**看板不联网**：全部数据来自本地 SQLite，刷新页面不消耗 API 免费额度，
数据源挂掉时看板仍能查看历史。实测最慢端点 25ms（预算 200ms）。

**口径说明**：强度榜展示的是**模型在用的泊松攻防强度**（`build_league_model`）。
Dixon-Coles 只修正低比分概率，**不改变强度值**，因此不存在「DC 版强度」这种东西。

**样本不足时不画假图**：已结算 <20 场、或本地已完赛 <60 场时，
对应卡片会明确显示「样本不足」而非画出看似可信的曲线。

**页面分区**：看板内容按主题分成 5 个区，顶部导航可一键跳转（窄屏横向滚动、页面滚动时吸顶）：

| 分区 | 内容 |
|---|---|
| 📅 赛程 | 每场一张卡片，含两队近 5 场胜负、实力分、排名、轮次与概率条；`今天 / 3 天 / 7 天` 切换 |
| 📈 模型表现 | 关键指标四宫格、Log Loss 趋势、校准曲线、各信心等级命中率 |
| 🧪 历史回测 | Walk-Forward 结论表（场次 / 命中率 / Log Loss / RPS） |
| 🔍 预测审计 | 最近已结算的预测 vs 实际赛果 |
| 🏆 球队强度 | 模型在用的攻防强度榜 |

分区标题由页面统一渲染，卡片内不再重复标题；宽屏（≥900px）趋势图与校准曲线并排双栏，窄屏单栏。

FastAPI 列在 `requirements-web.txt`，不混进 `requirements.txt`（机器人本体
不需要它）。但 Dockerfile 会**同时安装**两个文件 —— 看板与机器人必须同容器
运行，才能共用 /data 上的同一个 SQLite（Railway Volume 无法跨服务共享）。

## 模板层结构

模板层曾是一个 1135 行的单体类，现按**视图垂直切分**：

```
bot_handler.py (88 行)  ── 纯门面：Mixin 组装 BotUI + 兼容导出
├── templates.py (114)     静态文案与常量（零依赖，最底层）
├── formatkit.py (264)     原子工具：转义/概率条/队名/积分榜摘要
├── keyboards.py (118)     按钮键盘
└── views/ (5 个文件)      各视图：文案与它的组装逻辑同处一地
    common / prediction / analysis / fixtures / standings / menu
```

**为什么不把文案抽成 JSON/YAML**：实测文案行只占原文件 40%~60%，其余是循环与
条件分支；抽走文案后体积压不下来。更关键的是，文案与「在什么条件下说这句话」
强耦合——拆开后改一句文案要跨两个文件，反而更难维护。

按视图切分后，改文案只动 `views/` 里对应的一个文件；不引入模板引擎，
因此没有占位符拼写错误导致的运行时 KeyError（f-string 在编译期就能发现）。

**迁移已做等价性验证**：22 个视图方法在迁移前后输出逐字节一致
（含时间戳的方法归一化后比对），543 个测试全绿。

## 部署到 Railway

1. 服务连接到本仓库的 `main` 分支，构建方式为 Dockerfile。
2. 在 Railway 的 Variables 里填上面的环境变量。
3. **新建 Volume 并挂载到 `/data`**。注意挂载整个目录而非单个 db 文件——WAL 模式会生成 `football.db-wal`、`football.db-shm`，必须与主库一起持久化，否则可能丢最近未合并的写入。
4. **不要**给服务设置 Cron Schedule：这是长轮询的常驻进程，定时推送由程序内部完成。
5. 推送到 `main` 后 Railway 会自动构建并部署。部署后在 Telegram 里发送 `/status` 检查，再发 `/test` 验证整条链路。
6. **容器守护**：`start.sh` 用 `wait -n` 同时监视机器人与看板两个进程，任一退出即结束容器、由 Railway 重启。避免「机器人在推送、看板早已死掉」的静默失效。若 Web 打不开，先到部署日志确认 `[start] starting web dashboard` 是否出现。

验证持久卷是否生效：部署后发 `/storage`，**重新部署一次再发一次**，第二次若仍能看到第一次的标记文件及其时间，即证明 Volume 生效。

CI 与分支保护配置见 [`CI.md`](CI.md)。

## 模型说明

- 用积分榜（一次请求）得到每支球队的主/客场场均进球与失球，除以联赛平均得到攻防强度，并向 1.0 收缩（相当于补 5 场平均水平的先验比赛），避免赛季初样本太少。
- `λ主 = 主队主场进攻 × 客队客场防守 × 联赛主队场均进球`，`λ客` 同理；比分矩阵覆盖 0–10 球并归一化，汇总得到胜平负、最可能比分、大小球、双方进球概率。
- 赔率取各博彩公司「胜平负」盘口的中位数。**展示概率采用市场锚定融合**（`apply_market_adjustment(..., blend_weight=w)`）：`P_final = w·去水市场 + (1−w)·模型`，`w` 由 `MARKET_BLEND_WEIGHT` 配置，默认 **0.75**。在内置语料（英超近三赛季 1140 场，含 B365/Pinnacle 赔率）上的 walk-forward 实测：相对纯模型 **RPS 改善 0.0082、准确率 +1.87pp**，bootstrap 95% 置信区间不含 0。作为参照，纯市场 vs 纯泊松为准确率 53.78% vs 50.99%、对数损失 0.9692 vs 1.0053、McNemar p=0.007047，详见 `docs/MARKET_FUSION_EVAL.md`。模型原始概率原样保留在 `poisson_probs` 作为内部基准；无赔率时自动回落为纯模型，行为不变。
- 比分矩阵按胜/平/负三个结果块等比缩放，**缩放目标是融合后的概率**（`w=1` 时退化为纯市场），因此块和恰等于展示概率，最可能比分、大小球、双方进球与展示概率自洽，不会出现「最可能比分 1-0」与「客胜最高」并存。融合只改最终概率：`edge` 仍用模型自身概率计算，否则会系统性趋近 −抽水，价值投注功能等于废掉。
- **⚠️ Value Bet 标记已移除**。1110 场实测：按 `edge > 5%` 下注的 ROI = **−16.26%**，且阈值越高亏得越多（>10% −17.85%、>15% −20.61%）；对照组「无脑跟市场热门」为 −5.04%，与庄家抽水 5.48% 的理论下限吻合，说明市场接近有效、模型挑不出便宜。原 🚀 标记会把「模型与市场分歧大」误示为「有便宜可捡」，与实测结论相反。推送中改以「模型差异」客观陈述，分歧大时标 ⚠️（提示模型不可信，而非机会）。
- **Elo 融合**：赛果回写后更新各队 Elo 评分（基准 1500，主场加成 65 分，净胜球加权，新队 K=40 / 老队 K=20）。预测时用「份额归一」把 Elo 差融进 λ：主队进球占比按系数平移后按总进球数还原，因此 λ主+λ客 精确守恒，**不影响大小球判断**；系数夹在 [0.8, 1.25]，实测极端分差下胜率偏移不超过 ±7.4pp。
- **冷启动**：`python migrate_elo.py --dry-run` 可预览；正式执行会把库里已有的历史赛果按时间正序重放一遍，可重复执行（幂等）。免费套餐若拿不到历史赛季，机器人从 1500 分起步，靠 `PRIOR_GAMES` 收缩保证赛季初不失真。
- **⚠️ Elo 已实现但刻意未接入预测主流程**。回测（`机器人内 /backtest 命令`）在 7 个随机种子 + 真实结构数据上一致显示：接入 Elo 后对数损失、RPS、Brier、校准误差**全部变差**（对数损失改善均值 −0.0033），且 blend 参数扫描呈单调恶化（最佳值 0.0，即完全不用）。原因：积分榜攻防强度已充分捕捉球队实力，Elo 提供的是冗余信息加噪声。**在拿出有效证据前不接入**，避免让线上预测变糟。
- **回测方法**：滚动前进（walk-forward），预测第 i 场时只允许使用第 i 场之前的数据，杜绝前视偏差。主判据为对数损失与 RPS（越低越好），准确率仅作参考——准确率把「预测 30% 却说成 90%」和「诚实预测 30%」同等对待，会掩盖过度自信。
- **⚠️ Dixon-Coles 已实现但同样未接入预测主流程**（原因见下）。
- 尚未考虑：伤停、赛程密度、近期状态权重。**伤停能拿到并在深度分析里展示，但不参与概率计算**——`get_injuries` 只返回球员名与伤因，没有出场时间/身价等重要性字段，历史语料也无伤停字段，接进模型只能靠拍系数且无法回测验证；市场赔率已间接消化了伤停信息，融合市场概率是拿到该信息的成本更低且可验证的方式。

### 多模型集成与兜底（`ensemble.py`）

预测主流程不再只走一条路径，而是把**三路结果交给集成器合成**：

| 路 | 来源 | 定位 |
| --- | --- | --- |
| `model` | 泊松 + Elo + Dixon-Coles | 统计模型 |
| `market` | 多家博彩共识赔率去水 | 实测最强单模型 |
| `prior` | 联赛基线频率 | 冷启动 / 最终兜底 |

集成算法为**指数权重（Hedge / Multiplicative Weights）**：每路维护累积得分
（取 −RPS），权重 `w_i ∝ exp(η·score_i)`，理论 regret 上界 `O(√(T·ln N))`。
得分用**均值而非总和**——各路出场次数不同（市场常缺席），用总和会不公平地
放大出场少的路。

**分层兜底链**（任何情况下都出得来结论，绝不返回空）：

1. 某路缺失 → 该路权重归零，其余**重新归一化**（不是让空缺拖着预测走偏）
2. 无赔率 → 统计模型 + 基线接管
3. 一路都没有 → 联赛经验值 `(0.45, 0.27, 0.28)`

**⚠️ 诚实结论：集成无法超越纯市场。** 英超三赛季 1140 场 walk-forward 实测：

| 口径 | 准确率 | RPS |
| --- | --- | --- |
| 纯市场 | **54.04%** | **0.1955** |
| 集成（动态权重 η=200） | 53.60% | 0.1981 |
| 集成（等权平均） | 52.28% | 0.2049 |
| 纯泊松 | 50.83% | 0.2089 |

动态权重随 η 增大确实收敛到市场（η=100 → 0.492、**η=200 → 0.796**、
η=400 → 0.984），**与本项目既有的 `MARKET_BLEND_WEIGHT=0.75` 相互印证**——
两个独立途径得出同一个结论：市场该占大头。

所以集成带来的是**鲁棒性与兜底能力，不是准确率提升**。它的真实价值在
**市场缺席时**：此时统计模型集成 RPS 0.2087，略优于最好的单统计模型
泊松 0.2089。库里 5.9 万场里有赔率的只是少数，兜底不是理论风险。

真正的准确率增量只能来自**市场没有的信息**（首发阵容、伤停重要性、
xG 等实时数据），见下文「尚未考虑」。

**配置**

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `ENSEMBLE_LEARN` | 关 | 开启动态权重学习；关闭时用固定经验权重（市场 0.75），行为完全确定 |
| `ENSEMBLE_ETA` | 200 | 学习率 η。RPS 量级 0.2、模型间差距仅 0.01~0.02，η 太小权重分不开（η=12 时市场仅 0.49，近乎均分） |

**实现要点**：纯 Python —— `scipy` / `numpy` 都不在 `requirements.txt`，
生产环境导入会直接 `ImportError`。权重用**相对得分**（减去最大值后再取 exp），
否则 log 概率恒为负、η 稍大就会让所有路一起下溢成 0。

### 赛前实时信号：伤停与首发阵容（`prematch.py`）

模型原本只用「积分榜 + 近期战绩」估进球率 λ，这些都是赛前早已固化的信息。
赔率会吸收临近开赛的情况（这正是实测「市场 > 泊松」的原因），但**赔率只反映
共识，不包含我们对「这份缺阵名单到底多严重」的独立判断**。本模块把这些赛前
信号显式接入，让模型第一次拥有市场之外的信息：

| 信号 | 端点 | 说明 |
| --- | --- | --- |
| 伤停 | `/injuries` | 谁打不了（此前只用于展示，不参与计算） |
| 首发阵容 | `/fixtures/lineups` | 谁真上场、站什么位置、什么阵型 |
| 球队名单 | `/players/squads` | 补上伤停缺失的**位置**，使「前锋缺阵更致命」可加权 |
| 球员评估 | `/players` | 赛季累计 `games.rating`，按出场时间加权得首发真实实力 |
| 天气 | Open-Meteo | 温度/降水/风对总进球的抑制（**默认关闭**，见下） |

**作用点是进球率 λ，不是三项概率**：λ主 乘「主队进球系数（≤1）」与「客队
失球系数（≥1）」，λ客 对称处理。因此比分矩阵、大小球、BTTS 全部随 λ 一致
变化，不会出现「最可能比分 1-0 却说客胜概率最高」这类自相矛盾。主队缺员时
λ主 下降、λ客 上升，方向相反。

**额度保护**：官方说明阵容通常**开赛前 20–40 分钟**才公布，过早请求必然为空。
因此只有进入赛前 45 分钟窗口才去取，自动预测每轮数百场不会每场白试一次。

配置项：

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `PREMATCH_ENABLED` | 开启 | 关闭后行为与接入前**逐位一致** |
| `PREMATCH_STRENGTH` | `0.5` | 折损强度，`0` = 只接线不改结果（A/B 对照用） |
| `PREMATCH_TILT` | `0.0` | 阵型攻守倾向权重，默认不启用（比伤停更不确定） |
| `RATING_STRENGTH` | `0.5` | 球员评估强度，`0` = 只接线不改结果（A/B 对照用） |
| `WEATHER_STRENGTH` | `0.0` | 天气强度，**默认关闭**；启用前须在自己库上验证为正 |
| `PREMATCH_PUSH_ENABLED` | 开启 | 赛前二次推送总开关，关闭后只落库不推送 |
| `PREMATCH_PUSH_LEAD_MINUTES` | `60` | 距开赛多少分钟内允许推送 |
| `PREMATCH_PUSH_FORCE_MINUTES` | `20` | 始终拿不到阵容时的兜底推送点 |

**⚠️ 诚实边界（重要）**：

1. **权重未经本项目语料校准** —— 回测语料是英超 CSV，**根本没有伤停/阵容列**，
   无法用历史数据拟合。当前数值是保守量级，需线上积累 A/B 样本后重新定标。
2. **伤停端点不含球员位置**（只有缺阵类型），所以做不到「前锋缺阵影响更大」
   这类位置加权；位置信息只在首发阵容里有，而缺阵者按定义不在首发中。
   折损因此按固定比例分配到进球端与失球端。
3. **天气默认关闭（`WEATHER_STRENGTH=0`）** —— API-Football **没有天气端点**，
   管道已外接 Open-Meteo（免费、无需注册、不占足球额度），按「城市 → 经纬度 →
   预报」取数。但研究结论相互矛盾（英超样本显示降雨有微弱效应，英冠 4826 场
   样本显示**无统计显著性**），故**只搭管道、默认不改结果**。
   它是四类信号里**唯一能真正回测的**（Open-Meteo 归档回溯到 1940 年，而
   伤停/阵容/评分都不存在于任何历史语料），启用前应在自己库上验证为正。
4. **球员评估用的是赛季累计评分，不是单场评分** —— `/fixtures/players` 的
   `rating` 是**赛后**数据，赛前用会引入前视偏差，**绝不能用**。本模块改用
   `/players?team=&season=` 的 `games.rating`（只含已结束比赛的累计平均），
   赛前可用。代价是每场额外若干请求，故与阵容共用赛前 45 分钟窗口才取。

**伤停位置加权**依赖 `/players/squads` 把缺阵者 id 映射回位置。取不到名单时
自动**退化为按人数计**（权重 1.0），不会比不加权更差；缺阵者没有 id 时按中性
权重计入 —— 跳过会系统性**低估**缺阵。

**首发评分会自动量化主力缺阵**：缺阵者不在首发里，顶上来的替补评分通常更低，
加权均值自然下降，比「缺 1 人扣多少」精确得多。

无任何信号时所有乘数**精确为 1.0**（浮点精确，模型行为与接入前逐位一致），
该不变量由 `tests/test_prematch.py` 与 `tests/test_context.py` 共同锁死。

**赛前二次推送**：刷新只把新概率写进库，用户看到的仍是早上 08:00 那条 ——
信号接了等于没接。因此进入 `PREMATCH_PUSH_LEAD_MINUTES` 窗口后会推一次更新。
推送时机是**优先等阵容**：官方写明阵容开赛前 20–40 分钟才公布，T-60 拿到的
往往只有更新过的伤停与赔率，所以拿到阵容才立刻推；始终拿不到（部分赛事官方
不提供）则在 `PREMATCH_PUSH_FORCE_MINUTES` 兜底推一次，免得这场永远等不到更新。
同一场比赛**终身只推一次**，靠 `prematch_push` 表去重 —— 赛前刷新 15 分钟一轮，
不去重就是刷屏。标记在**发送成功后**才写：标记早于发送会把一次失败变成永久
不再推送。由 `tests/test_prematch_push.py` 锁死。

### 赛前信号对照（signal_ab）：把拍脑袋的权重换成算出来的

上面那些保守权重是**猜的**。要换成用真实数据算出来的权重，唯一靠谱的办法是
**影子对照**：每次真正施加信号时，同时算一份「假如不施加」的预测，两版都存下
来，赛后比谁更准。

**表设计（`signal_ab` 表）**：

| 设计点 | 决定 | 原因 |
| --- | --- | --- |
| 粒度 | 一行 = **一场比赛 × 一种信号** | 同一场会同时触发伤停与阵容，混在一行就无法拆开评估每种信号的价值 |
| 强度 | 存**原始值**（`signal_strength`） | 归一化逻辑会变，原始值永远能重新算；归一化值另存一列仅作展示 |
| 重复触发 | **UPDATE 同一行**，不 INSERT | 否则同一场多条记录，复盘不知道该用哪条 |
| 信号消失 | 标 `change_type=revoked` | 伤停球员赛前复出也是一次变化；不记录会把「撤销后仍命中」错算成「信号有效」 |
| 算出一半 | 标 `status=partial_failure` | 必须区分「信号没用」和「信号根本没算出来」，后者是 bug |
| 新增类型 | `signal_type` 用**字符串** | 将来加天气不需要改表结构 |
| 时间 | 全部 **UTC** | 混用 UTC 与本地时间是最容易出诡异 bug 的地方 |
| 归档/测试 | 预留 `is_archived` / `is_test` | 现在不处理，需要时不用改表；测试数据必须能过滤掉，否则污染线上统计 |

**写入失败绝不阻断预测** —— 对照是为了「以后能变好」，它挂了最多是以后没数据，
不能让今天的预测发不出去。

**回填**：比赛结束后自动写回 `actual_home/actual_away`，只更新尚未结算的行
（不会覆盖已有比分），失败的留在 `unsettled` 队列里下次再试。

**复盘口径**：命中率的**主指标只统计强信号场**（强度 ≥ `SIGNAL_STRONG_THRESHOLD`，
默认 0.15）—— 弱信号本来就不该产生明显影响，混进来只会稀释信噪比。同时保留
「全部触发场」的口径供对照。`pure_baseline`（无任何信号）与 `partial_baseline`
（有他类信号、独缺本类）两版都存，分析时用哪个取哪个。

**防作弊**：复盘统计只基于库里**已存下的记录**，绝不重新跑一遍预测来算 ——
重跑会受当前代码逻辑影响，答不出「当时那个版本的信号到底有没有用」。

**信号撤销（revoked）**：伤停球员赛前复出、名单更新后某类信号消失，本身就是
一次变化。`capture()` 会比对「上一轮还标 applied、这一轮已不在激活集合」的
类型，补写一行 `change_type=revoked`（强度记 0，说明文字写明已撤销）。

这类行**一律排除在统计之外**：信号已经被撤下，我们发出的预测里不含它了，
而「如果它还在会怎么说」无法反推。把它算进去会把「信号撤销后仍然命中」
错记成「信号有效」，让结论系统性偏乐观。撤销数在 `--stats` 里单独显示，
审计与排查仍看得到，只是不参与「有没有用」的判断。

撤销行只在**状态真的发生变化**时写一次：写完后 `change_type` 已变成
`revoked`，下一轮比对时不再命中，不会重复计数。

配置项：

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `SIGNAL_AB_ENABLED` | 开启 | 关闭后不再写入对照记录（预测行为不变） |
| `SIGNAL_STRONG_THRESHOLD` | `0.15` | 强信号阈值，主指标只统计达到该强度的场次 |
| `SIGNAL_MIN_SAMPLES` | `30` | 复盘「样本不足」阈值，低于该值只报数量不报命中率 |
| `SIGNAL_AB_WRITE_ENABLED` | 关闭 | 权重**写**权限，默认只读；开启后才允许改信号权重 |

### 权重治理：先模拟、再确认、只追加

调权重是本项目**唯一会真实改变预测结果**的操作，比改代码更危险 —— 代码错了
测试会失败，权重错了只是悄悄变差。故设三道关：

1. **默认只读**：`SIGNAL_AB_WRITE_ENABLED` 默认关闭，线上服务不给写权限，
   任何代码 bug 都不可能意外改掉权重。
2. **先模拟**：`signal_admin.simulate_weight()` 算出"如果应用新权重，过去 N 场
   会怎样"，看过模拟结果再决定。⚠️ 模拟是**线性近似**（没存 λ，只能按
   `partial + (signal − partial) · w_new/w_cur` 缩放），只能判断方向，不能当最终数值。
3. **二次确认 + 只追加**：`apply_weight(confirm=True)` 才真正写入；每次变更
   （含"仅建议"）都进 `signal_weight_log`，旧值永久保留。

**采集链路**：`service._predict_one` 在 `predict_match` **之后、市场融合之前**
调用 `signal_capture.capture()` —— 必须卡在这个位置：再往下 `analysis` 就被

### 已实现但未接入的两个模块（原因与证据）

| 模块 | 回测结论 | 处置 |
| --- | --- | --- |
| Elo 评分 | 7 种子 ΔLogLoss 均值 **−0.0033**，0/7 为正 | 不接入 |
| Dixon-Coles | 7 种子 ΔLogLoss 均值 **+0.0015**，**6/7 为正**，t=1.89 | 暂不接入（未达显著性死线） |
| 射正强度（`exp_shot_quality.py`） | ΔRPS −0.0011，95%CI 含 0 | 不接入 |

**为何不接入 Dixon-Coles**：接入标准为「7 个以上随机种子 ΔLogLoss 均为正，且统计显著（t>2.5）」。
实测 seed 99 为 −0.00106，t=1.89，**未达死线**。它有真实的方向性收益（6/7 正，远好于 Elo 的 0/7），
但效应量被 λ/μ 估计误差淹没：`ρ` 的真实效应仅在 |ρ|≥0.15 时才显著
（ρ=−0.15 时 +0.00244，t=+4.46；ρ=−0.10 时 +0.00089，t=+2.10）。
**在拿出更强证据前不接入**，避免以「准确率提升」为由做伪增强。

**Dixon-Coles 实现已按 Dixon & Coles (1997) 原文严格完成**，可随时启用：
- 修正项 τ 覆盖 0-0 / 1-0 / 0-1 / 1-1 四个格子，`tests/test_dixon_coles.py` 用手算值逐项验证（精度 1e-12）
- `ρ` 由黄金分割搜索最大化对数似然拟合（大样本无偏：n=3000 时估计 −0.096 对真实 −0.10）
- `ρ` 自动夹紧到可行区间，保证全部 τ ≥ 0；NaN / 极端 λ 安全退化
- 单场延迟增量 **0.0091 ms**（预算 10ms）
- ρ=0 时与纯泊松逐元素等价，向后兼容

**为何不接入射正强度**（2026-10-14 实测，`exp_shot_quality.py` 可复现）：
假设「射正（场均 4.5）比进球（场均 1.5）更能稳定估计球队创造机会的能力」。
用英超三季真实语料、严格走前（第一整季仅作热身，评估 760 场）实测：

| 口径 | RPS | 命中率 | ΔRPS vs 进球基线 | 判定 |
| --- | --- | --- | --- | --- |
| 进球（基线） | 0.2343 | 41.45% | — | — |
| 射正 | 0.2342 | 40.13% | −0.0001 | 不显著 |
| 进球×射正融合 | 0.2331 | 41.32% | −0.0011 | 不显著 |
| 市场赔率 | 0.2014 | 51.58% | −0.0330 | **显著** |

**最值得记住的教训**：热身期设为 40 场时，融合口径 ΔRPS −0.0048 且
**置信区间不含 0，看似显著**；把热身放宽到整季后，同一指标退化到 −0.0011
且不显著。那点收益只是在补偿「基线强度还没攒够」，并非射正真携带额外信息。
**热身期太短会制造假的改进**——凡走前回测，务必确认热身期足够长。

## 常见问题

- **`HTTP 403`**：RapidAPI 通常表示这个 Key 没有订阅 API-Football，或填错了 Key。到 RapidAPI 控制台确认订阅，或改用官方直连并设置 `API_FOOTBALL_KEY`。
- **`HTTP 429`**：请求太频繁或当日额度用尽。免费套餐额度很小，程序已对赛程、积分榜、赔率做了缓存。
- **提示套餐不支持该赛季**：免费套餐可能不开放当前赛季，需要升级套餐。
- **收不到定时推送**：发 `/status` 看「下次推送」时间；进程重启会重新计时，错过的时间点不会补发。
